# System Patterns

- FastAPI uygulamasi server-rendered Jinja2 ekranlari ve hafif JSON API sunar.
- SQLite erisimi repository katmaninda toplanir.
- Import/fatura donemleri `import_batches` tablosunda, kayitlar `invoice_records.batch_id` ile tutulur.
- Import ve validasyon servisleri UI route'larindan ayridir.
- Import akisi dosya inspection, sheet secimi ve explicit kolon mapping destekler; alias mapping fallback olarak kalir.
- Secim kurallari `SelectionService` icinde tutulur; repository sadece kontrollu PENDING/SELECTED gecislerini uygular.
- Secim ve batch hazirligi aktif fatura donemi baglaminda calisir.
- Playwright lifecycle `BrowserManager` icinde tutulur.
- Portal login ve manuel 2FA state akisi `PortalSessionManager` uzerinden yonetilir.
- e-Arsiv sayfa navigasyonu `EArchiveNavigation`, form doldurma `InvoiceFormFiller`, hata hook'lari `PortalErrorDetector`, tek kayit orchestration `DraftCreator` icinde tutulur.
- Portal retry/backoff ihtiyaci `utils.retry.retry_with_backoff` ile kucuk ve hedefli tutulur.
- Navigation hazir kontrolu tek alan yerine birden fazla kritik form alanini dogrular.
- KDV 0 sonrasi gelen istisna bilgi mesaji `PortalErrorDetector` tarafindan zararsiz portal bilgisi olarak kapatilip yoksayilir.
- TCKN sonrasi `#txtTaxSchemeName` doluysa Turmob sorgusu atlanir; mevcut portal ad/soyad alanlariyla dogrulama devam eder.
- Turmob sonrasi ad/soyad kontrolu `InvoiceFormFiller` icinde yapilir; uyusmazlik typed exception ile status'a map edilir.
- Ad/soyad karsilastirmasi iki katmanlidir: once `normalize_person_name` (strip + bosluk + casefold) ile birebir, olmazsa `normalize_person_name_tolerant` (NFC + `ı/İ/I->i`, `ü/Ü->u`, `ö/Ö->o` + ayni normalize) ile toleransli. Toleransli eslesme WARNING logu ile kabul edilir; diger harf farklari (ş/ç/ğ dahil) bilincli olarak tolere edilmez.
- Tek kayit draft DB/status akisi `SingleDraftService` ile repository'ye yazilir.
- Gercek portal dialoglari `PortalErrorDetector` tarafindan okunur, OK ile kapatilir, screenshot alinir ve typed exception'a donusturulur.
- Coklu isleme `BatchRunner` tarafindan sirali olarak yapilir; runner tek kayit akisini `SingleDraftService` uzerinden cagirir.
- Sync Playwright thread'e baglidir: tum Playwright giris noktalari `@on_playwright_thread` ile `playwright_worker` tek kalici thread'ine yonlendirilir. Worker uzerinden yapilan ic ice cagrilar inline calisir; batch job aktifken diger thread'lerden gelen cagrilar `PlaywrightWorkerBusyError` ile hemen reddedilir.
- Batch request icinde calismaz: `BatchJobManager` job'u worker'a arka plan isi olarak verir, ayni anda tek aktif job'a izin verir, ilerlemeyi bellekte tutar ve `cancel_event` ile kayitlar arasinda durdurur. Portalda islenen kayit her zaman tamamlanir.
- Idempotens DB seviyesinde saglanir: `claim_for_processing` tek kosullu UPDATE ile sadece PENDING/SELECTED kaydi IN_PROGRESS'e alir. Cift tiklama veya es zamanli istek ikinci kez portala gitmez.
- Taslak Kaydet tiklandiktan sonra sadece acik portal reddi temiz hata sayilir; diger her belirsizlik `DraftSaveUnconfirmedError` -> `NEEDS_REVIEW` olur. NEEDS_REVIEW otomatik yeniden denenmez ve `RETRYABLE_STATUSES` disindadir; sadece operator "Taslak var/yok" ile kapatir.
- Basari DB yazimi portal try blogunun disindadir; boylece basarili taslak hicbir zaman FAILED isaretlenmez.
- Uygulama acilisinda (FastAPI lifespan) IN_PROGRESS kalmis kayitlar NEEDS_REVIEW'e cekilir; job beklenmedik hatayla biterse ayni kurtarma hemen calisir.
- Import once tum satirlari dogrular, sonra batch ve kayitlari `create_import` ile tek SQLite transaction'inda yazar.
- UI importu onizlemeden gecer: tablo durumu tarayicida, dogrulama kurallari sadece `check_preview_rows` icinde (canli `/import/check` ve son `import_preview_rows` ayni fonksiyonu kullanir). Tabloda ne gorunuyorsa o aktarilir; tek hata varsa hicbir sey yazilmaz.
- Additive migration'a bagli index'ler (`idx_invoice_records_batch_id`) SCHEMA_SQL'de degil, migration sonrasinda olusturulur.
- `BatchRunner.run()` sadece batch isleme sirasinda `SleepPreventionGuard` context manager'i acarak bilgisayarin uyumasini engeller ve cikista otomatik kapatir.
- Sleep prevention macOS icin `caffeinate`, Windows icin `SetThreadExecutionState`, Linux icin `systemd-inhibit` kullanir.
- Batch raporu `BatchReportService` ile status dagilimi ve kayit detaylarina donusturulur.
- UI batch run, session READY degilken kullaniciyi `/session` ekranina yonlendirir; backend runner yine session check ile guvenli abort uretir.
- Ana UI bilgi mimarisi donem merkezlidir: donem listesi -> donem sayfasi (kisiler + tum aksiyonlar); ayrica tum kayitlar, dosya yukle ve portal sayfalari. POST aksiyonlari PRG ile `?msg=` flash mesajina doner.
- Status kodlari UI'da `constants.STATUS_LABELS` ile Turkce etikete cevrilir; ham kod sadece `title` attribute'unda.
- UI gorsel sistemi tek `static/css/app.css` (Bootstrap yok); server-rendered Jinja yapisi korunur. CSS URL'i `CSS_VERSION` ile cache-bust edilir.
- Ana layout ust navbar, 4 adimli is akisi, Bootstrap kart/form/alert/table/badge bilesenleri ve tutar/status kartlariyla kurumsal operasyon paneli seklinde calisir.
- Durum degerleri `InvoiceStatus` enum'u ile merkezi tutulur.
- Portal otomasyonu `automation/` katmaninda Playwright ile ayrilir.
- Kayit bazli hatalar batch'i durdurmaz; session-level veya temiz form reset hatalari batch'i guvenli durdurur.
- Yerel veri silme `RecordCleanupService` uzerinden yapilir: IN_PROGRESS kayitlar ve aktif batch job'un donemi silinemez; silme portal taslaklarini etkilemez.
- Yikici UI aksiyonlari `data-confirm` ile onay ister; ortak handler `base.html` icindedir.
